# 大文本源码页虚拟化

**Status**: accepted（2026-10-20）

打开非 Markdown 文本时，服务端 TTFB 只有 9–60 ms，但浏览器完整加载 1 MB `.txt`
要 **42.5 秒**；跳过 highlight.js 后同页只要 **268 ms**。根因是 highlight.js 对
没有语言标识的整段源码做 `highlightAuto`，以及一次性创建所有行号 DOM。
10 MB 文本即使不高亮，全量 DOM 也要约 4.2 秒。

用户不接受“大文件改为下载”的降级，因此需要保留完整源码可读性。

## 决定

1. **大文本源码页虚拟化**：源码页超过 **256 KB** 时，服务端只渲染前
   **1000 行**作为无 JS 回退，并输出 `source-virtual` 容器；浏览器通过
   `?text=1` 取回完整文本，只渲染视口附近的约 90 行（21px 固定行高、上下 overscan）。
2. **行锚点保留**：虚拟行保留 `id="L<n>"`；加载完成后处理 `#L<n>` 深链，
   搜索结果与源码页行号跳转继续可用。
3. **不做自动语言探测**：源码页与 Markdown 代码块都只在存在明确
   `language-*` 类时调用 `highlightElement`；无语言/未知语言保持纯文本。
   这与 VS Code Markdown 预览的 highlight 回调一致。
4. **高亮大小上限**：单个代码块超过 **256 KB** 跳过高亮，语言条标注
   “未高亮”；小文件仍保留语法高亮。
5. **文本通道**：`GET /x?text=1` 返回 `text/plain; charset=utf-8`，只对
   Markdown/文本生效；CSP 增加 `connect-src 'self'`。
6. 无 JS 时仍能读前 1000 行并下载原文；完整内容需要 JS 虚拟列表。

## 考虑过的替代方案

- **超过 2–5 MB 直接下载**：最快且最简单，但用户明确不接受牺牲预览能力。
- **仅关闭自动探测**：解决 1 MB `.txt` 的 42 秒，但 5–10 MB 全量 DOM 仍需
  1.5–4.2 秒，且大文件无法滚动阅读。
- **服务端分页**：无 JS 也能翻页，但需要维护分页 URL/状态；当前选择 JS 虚拟化 +
  首屏回退，交互更接近编辑器。
- **服务端流式/分块加载**：网络更省，但实现复杂；本地服务 20 MB 一次性 fetch
  足够快。

## 后果

- 1 MB 文本源码页从 **42.5 s** 降到约 **0.13 s**；10 MB 约 **0.10 s**（本机基准）。
- 虚拟化模式只显示纯文本，不做语法高亮；小文件与明确语言的代码块仍有高亮。
- 无 JS 的源码页只显示前 1000 行；这是可访问性/降级上的明确边界。
- 需要维护 `?text=1` 路由、CSP `connect-src`、虚拟列表与深链测试。
- 性能预算脚本 `tests/perf-source.mjs`：100 KB/1 MB/10 MB/1 MB Rust；
  CI Linux 运行宽松上界，防止 42 秒级退化回归。
