# 大文本源码页：全文分块 + content-visibility

**Status**: accepted（2026-10-19；2026-10-20 修订，取代“服务端前 1000 行回退 +
客户端虚拟列表”的首版方案）

打开非 Markdown 文本时，服务端 TTFB 只有 9–60 ms，但浏览器完整加载 1 MB `.txt`
要 **42.5 秒**；跳过 highlight.js 后同页只要 **268 ms**。根因是 highlight.js 对
没有语言标识的整段源码做 `highlightAuto`，以及一次性创建所有行号 DOM。
10 MB 文本即使不高亮，全量 DOM 也要约 4.2 秒。

用户不接受“大文件改为下载”，也不接受服务端只输出前 1000 行、其余内容依赖
JS 再取的降级：无 JS 或 JS 失败时页面会被截断。因此目标改为
**服务端始终输出全文，同时保持大文件的滚动与首屏性能**。

## 决定

1. **全文分块渲染**：源码页超过 **256 KB** 时不再截断，而是按
   **500 行/块**输出 `<section class="source-chunk">`。每个块声明
   `data-start`、`data-rows` 与 `--rows`，CSS 使用
   `content-visibility: auto` + `contain-intrinsic-height` 跳过离屏块的布局与绘制。
   行高固定为 21px，保证滚动条高度与块内定位稳定。
2. **无 JS 全文可读**：初始 HTML 就包含完整源码、行号与总行数；不依赖 fetch、
   不依赖 `?text=1`。CSP 因此不放宽 `connect-src`。
3. **渐进增强**：`web/src/islands/source.ts` 只对可见/邻近块创建 `id="L<n>"` 行号锚点，
   并处理 `#L<n>` 深链（按行号定位块、滚动到该行、给行号与代码行加目标高亮）。
   未浏览到的块不产生行号 DOM。
4. **按块懒高亮**：仍不做自动语言探测；只有存在明确 `language-*` 时才调用
   `highlightElement`。大源码在块进入视口附近时逐块高亮，单块仍有 256 KB 上限；
   无语言文件保持纯文本。
5. **小源码保持原样**：≤256 KB 继续使用服务端行号锚点 + 一次性客户端高亮。
6. **无独立文本通道**：删除 `GET /x?text=1`；`?download=1` 仍用于下载原文。

## 考虑过的替代方案

- **服务端只渲染前 1000 行 + 客户端取全文**（首版）：首屏最快，但无 JS 时内容
  被截断，用户明确拒绝；也引入了 `?text=1` 与 `connect-src` 的额外面。
- **超 2–5 MB 直接下载**：最快且最简单，但用户明确不接受牺牲预览能力。
- **服务端为每一行生成锚点**：无 JS 深链最完整，但 10 MB 文本要创建约 18 万个
  元素；实测首屏约 0.46 s、滚到底约 2.1 s，明显差于懒锚点方案（约 0.11 s /
  0.15 s），因此只在 JS 可见块中生成。
- **服务端分页**：无 JS 可翻页，但需要维护分页 URL/状态，阅读体验不如连续全文。
- **服务端流式输出**：可降低首字节与内存峰值，但浏览器仍要解析全文；当前
  一次性输出已满足本机性能预算，留作后续优化。

## 后果

- 1 MB 文本源码页从 **42.5 s** 降到约 **0.08 s**；10 MB 约 **0.11 s**
  （本机 headless Chrome 基准，含完整 HTML 解析）。
- 初次响应携带完整源码，网络传输量随文件大小线性增长；这是“无 JS 也完整”
  的直接代价，压缩/流式可作为后续优化。
- 无 JS 时全文可读，但没有精确行号深链与按块高亮；这两项是 JS 增强。
- 性能预算脚本 `tests/perf-source.mjs` 的 10 MB 用例会检查末行标记，
  防止重新引入静默截断。
- 需要维护分块 CSS（`content-visibility`、固定行高）、懒锚点/深链与按块高亮测试。
