# markdown 目标路径的编码语义：以 VS Code 预览为准

**Status**: superseded by [ADR 0005](0005-vscode-1.142-as-oracle.md)

> **新实现注意**：Rust 重写按 VS Code 核心语义，相对路径改为**解码两次**
> （硬边角见 [ADR 0007](0007-hard-edge-cases-use-comrak.md)）。本文保留旧 Python 实现的
> 决策记录；其中“只解一次”的偏离不再适用于新实现。代价是：文件名里**字面**含
> `%xx` 的文件（例如 `x%20y.png`）不能通过相对 Markdown 目标到达 —— 作者写
> `x%2520y.png` 会被解成空格，写 `x%20y.png` 也指向空格文件。这是跟随 VS Code
> 双重解码的 accepted deviation；需要访问这类文件时用目录索引或绝对 URL。

渲染一个 markdown 目标要经过四步：**切分 `?`/`#` → 解码 → 相对解析 → 编码**。
顺序放错就会产出指向不存在文件的 URL，而这一步恰恰是链接与图片一度分叉的地方。
本决定把顺序钉死为「**先切分原始文本，只对 path 段解一次百分号，再编码一次**」，
并把链接、图片、引用式、目录索引四条路收敛到同一个函数。判据不是「哪种更规范」，
而是 **VS Code 1.141 的预览实际怎么做**：`%20` 表示空格，`](<a b.png>)`（VS Code
把文件拖进编辑器时写出的形式）必须能加载，`a%23b.md` 这种文件名必须链得到。

## 考虑过的替代方案

- **直接引入 markdown-it**（VS Code 内置的解析器，14.3.2，MIT）：能一次拿到全部解析对齐，
  也曾被选中。放弃的原因是它推翻这个项目的第一前提 —— 零第三方文件、只用 Python 标准库、
  内网离线可审计（README §1 的选型表里明确拒绝的就是它）；markdown-it 是 JS，要跑它就得
  再引入 node 或内嵌 JS 引擎，等于把被拒绝的方案换个形式接受。改用**借它的行为当判卷标准**：
  期望值由 markdown-it 14.3.2 实测生成后固化进测试，运行时与测试都保持零依赖。
- **目标原样直通**（既不解码也不编码）：对 `%20` 的结果碰巧相同，但裸空格、`<>` 里的空格、
  非 ASCII 都会以未编码形态写进 HTML 属性，与目录索引的编码规则不一致，「四处统一」名不副实。
- **解码后按白名单规范化重编码**：URL 更整齐，但会让文件名里字面含 `%xx` 的文件不可达，
  属于行为回退。

## 一处有意偏离 VS Code

VS Code 的相对路径实际解码了**两次**（`Uri.parse` 一次、webview 资源宿主一次），于是文件名里
真含 `%20` 的文件在它那里用相对路径**打不开**。我们只解一次：`a%2520b.png` 能命中字面
`a%20b.png`。跟了它就是丢能力，所以不跟 —— 差异与其余边角一起记在 README §9。
