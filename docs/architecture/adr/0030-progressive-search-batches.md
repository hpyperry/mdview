# ADR 0030：搜索分批扫描与渐进追加

- Status: accepted
- Date: 2026-11-07

## 背景

`search_files` 原先一次遍历整个 root，读取所有 Markdown/文本文件后才返回。工作目录
很大时，即使用户只需要前几条结果，请求也会卡到全树扫描结束；已有的 40 组/200 条
上限只能限制最终输出，不能限制扫描成本。

## 决定

### 1. 每批硬预算

- 最多扫描 **2000 个文件**；
- 最多耗时 **约 1.2 秒**；
- 最多返回 **40 个文件组**、**200 条结果**；
- 单文件最多 **5 条**命中；
- 任一上限触发即停止当前批次，并标记 `more=true`。

### 2. cursor 续扫

- 遍历使用 `WalkDir`，顺序确定；
- 响应携带 `next_cursor`（已消费的 walker 条目数）；
- 「继续搜索」链接带 `?cursor=N`，下一次从第 N 个条目继续；
- cursor 上限 1,000,000，避免异常大值；
- 跳过的条目只走 metadata，不读文件内容；后续批次仍有遍历成本，但不会再读已跳过
  文件。

### 3. 渐进展示

- 服务端渲染当前批次，并在结果底部输出 `.search-more-wrap`：
  - 说明“已扫描前 N 个文件，当前显示这一批结果”；
  - 「继续搜索」链接；
- 搜索岛拦截链接点击，`fetch` 下一批 HTML，解析 `.result-group` 追加到列表，
  重新标记关键词并更新页头文件数/结果数；
- 没有 JS 时链接直接导航到下一批；功能仍可用，但只显示该批结果（不保留上一批）。
- 首批没有结果但 `more=true` 时，不显示“没有找到”，而是提示已扫描的文件数并允许
  继续。

## 备选方案

- **一次性全树扫描 + 只限制输出**：输出变小但延迟不变，解决不了大目录卡顿。
- **服务端后台任务 + 轮询/SSE**：可以做到更细粒度，但需要任务生命周期、取消、
  临时状态与更多前端代码；当前收益不足。
- **全量结果缓存后分页**：首次仍要全树扫描，违背目标。

## 后果

- 大目录首屏有明确上限，不再无限等待；
- 结果可能不是全局排序后的前 N 条，而是按遍历顺序分批，再在批内排序；
- 用户可通过「继续搜索」看更多；无 JS 时是分页行为；
- 跳过 cursor 的遍历成本仍存在，后续可考虑持久化/WalkDir 续游标。
