# 内部 URL 用查询参数消歧，真实文件优先

**Status**: accepted（2026-10-21）

`/search`、`/_nav`、`/_assets/*` 既是 mdview 的内部页面/接口/资产地址，也可能是
服务根里的真实文件或目录。保留路径会让同名文件永远无法通过自然 URL 打开；
统一前缀只是把冲突收窄到一个前缀，仍然会撞上同名目录。决定保留现有路径，用
查询参数标记内部请求，让真实文件优先。

## 决定

1. 内部请求必须带 `__mdview` 查询参数，值只能是 `search`、`nav`、`asset`：
   - 搜索页：`/search?__mdview=search&q=…`
   - 导航 JSON：`/_nav?__mdview=nav`
   - 内嵌资产：`/_assets/<name>?__mdview=asset&v=<version>`
2. 不带 `__mdview`（或值不匹配）的请求按普通文件路径处理：真实文件/目录存在就
   走现有文件管线；不存在就 404。不提供内部回退，也不重定向到带标记的 URL。
3. 真实路径与内部路径同名时，文件/目录占用自然 URL；内部功能只在带标记的 URL
   上可用。目录语义不变：例如真实目录 `search/` 的 `/search` 仍 301 到
   `/search/`，搜索页用 `/search?__mdview=search`。
4. 页面生成的所有内部 URL 都带标记：搜索图标与表单、导航 fetch、CSS/JS 资产链接。
   搜索页自身也带标记。
5. `--no-search` 只关闭带 `__mdview=search` 的搜索页；不带标记的 `/search` 仍是
   普通文件路径。
6. `__mdview` 是保留查询键；标记不是安全边界，不改变 Trust、CSP 或路径夹紧规则。
7. 旧的不带标记 URL 不再作为内部功能别名。旧 `/search?q=…` 书签、旧 `/_nav`
   调用和旧缓存页面里的 `/_assets/...` 请求会失效；这是有意的破坏性变更。

## 考虑过的替代方案

- **保留路径并写文档**：同名真实文件不可访问；否决。
- **统一前缀 `/_mdview/*`**：冲突收窄但没消失，真实 `_mdview` 目录仍被占用；
  否决。
- **根路径查询命名空间**（`/?q=…`、`/?__mdview=nav`）：同样零冲突，但搜索页和
  资产 URL 全部变化，根路由承担更多分发；保留现有路径的迁移更小，否决。
- **随机前缀 `/_m-<token>/*`**：实际不会撞名，但 URL 每次启动变化，浏览器探针
  与缓存调试更复杂；否决。
- **无标记时文件优先、缺文件回退内部**：旧链接兼容，但同一内部功能有两个 URL，
  且“保留路径”的语义含糊；用户选择严格 404，否决。

## 后果

- 同名文件/目录与内部功能都能用，不再需要“保留命名空间”的概念。
- 旧 URL 是破坏性变更；README、AGENTS、测试与浏览器探针必须同步到带标记 URL。
- 升级后仍打开的旧页面可能请求不带标记的 `/_assets/...` 而 404；页面本身是
  `no-store`，刷新即可。
- 实现时 `/search`、`/_nav`、`/_assets/*` 的 handler 先检查标记；无标记时转交
  普通文件处理。带标记的内部请求不做文件系统解析。
